File and record format ​

This page describes the current version-1 layouts. Use format parsing APIs instead of duplicating offset calculations in application code. Multi-byte integers and stored values use little-endian representation.

Matrix stream: CPK ​

A .cpk stream has a 4096-byte superblock, page-aligned chunks, and a final chunk directory. Offsets are relative to the start of the stream, including when the stream is embedded inside another file.

Superblock offsetField
0Four-byte magic CPK\0
4Version u16
6Flags u16, currently zero
8Page size u32
12Dtype code u8
13Source layout code u8
14Reserved u16
16Row count u64
24Column count u32
28Chunk count u32
32Target chunk rows u32
36Reserved u32
40Directory offset u64
48Stream length u64
56Non-cryptographic hash of the first 56 bytes and directory

The writer starts with an invalid superblock and writes the valid one last. The hash protects header and directory consistency; it is not a cryptographic or whole-record payload integrity check.

Dtype codes, in order, are U8, U16, U32, U64, I8, I16, I32, I64, F32, F64 (0 through 9). Source layout describes CSR or dense input. Neither dtype nor source layout determines an individual record's sparse/dense coding choice.

Each 40-byte directory entry contains:

FieldWidth
First row8 bytes
Chunk offset8 bytes
Total chunk length8 bytes
Metadata length8 bytes
Row count4 bytes
Reserved4 bytes

Chunks cover consecutive rows in order. The directory ends the stream.

Chunk: CPAK ​

A chunk begins with a 64-byte header using magic CPAK and version 1. Flags indicate a column permutation and column-mode values. The header declares row and column counts, value width, rANS lane settings, page size, row bounds, total nnz, metadata length, and record-region length.

Metadata then contains:

  1. Three 256-entry u16 rANS frequency tables: gaps, ranks, and dictionaries. A used model sums to 2^11; an unused one sums to zero.
  2. An optional coded-to-source column permutation.
  3. Optional per-column mode values.
  4. Per-record offsets (u64), lengths (u32), and kind flags (u8).
  5. A cumulative u64 nnz table of n_cells + 1 entries.
  6. Padding before a page-aligned records region, when paged.

Column ids use two bytes through 65536 dimensions and four bytes above that. Offsets and cumulative nnz tables are 8-byte aligned. Section offsets are derived from chunk shape rather than stored independently.

With page_log2 = 0, records are contiguous in row order. With paging enabled, the records region starts at a page boundary; records can appear in another physical order with gaps. The offset/length tables identify them. Supported packed page sizes are powers of two from 512 to 65536 bytes.

Record ​

A nonempty record starts with:

Flag bitsEncoding
0–1Index mode: raw (0), gap-coded (1), dense (2)
2–3Value mode: raw (0), dictionary-coded (1), column-mode-coded (2)
4–7Reserved, zero

A sparse record has stored elements in coded column order. Explicit stored zeros remain elements. A dense record has no index section and stores one value per dimension; its nnz counts nonzero values, while its element count is the full dimension. Empty rows can have a zero-length record.

Dictionary coding stores distinct value bit patterns and per-element ranks. Column-mode coding uses rank zero for that column's mode and positive ranks for exceptions in a record-local dictionary. rANS state capacity can carry leading escape or pool bytes; consumers should use the provided decoder rather than treating these as independent byte streams.

Parsing and ownership ​

parse_meta validates chunk-level structure and returns a borrowed view. OwnedMeta keeps owned bytes for longer-lived metadata. Superblock and ChunkEntry expose matrix-level fields. Record paths retain the trusted-data contract described in codecs; metadata validation is not validation of every inner record byte.

API: format module, Superblock, ChunkEntry, Meta.
